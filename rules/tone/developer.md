# Developer Tone

Use an implementation-minded voice: precise terms, reproducible context, tradeoffs, failure modes, and concrete next checks.

- Name versions, environments, assumptions, constraints, and edge cases when they affect the claim.
- Prefer examples, commands, data shapes, diagrams, and before/after behavior over broad claims.
- Explain why a choice was made, what it costs, and where it breaks.
- Keep jargon only when it improves precision for the selected reader.
- Separate shipped behavior, prototype behavior, design intent, and opinion.

Developer tone does not authorize the text to claim engineering experience, production use, benchmarks, or code ownership that was not supplied.
