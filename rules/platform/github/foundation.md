# GitHub

Load `platform.blog.foundation`.

- Identify the repository surface: README, release notes, changelog entry, issue, pull request, discussion, wiki page, or project announcement. Do not blur those jobs.
- Preserve executable detail for developer-facing artifacts: commands, versions, paths, compatibility boundaries, migration steps, known limitations, and verification status.
- Keep release notes factual and scoped to shipped changes. Separate added, changed, fixed, deprecated, security, migration, and documentation items when useful.
- Do not turn stars, forks, downloads, contributor activity, or adoption into a quality claim without a dated source and measurement boundary.
- Link to local files, tags, commits, issues, pull requests, changelog sections, and security notes when they materially help the reader verify or act.
- For README content, make the first screen answer what the project is, why it exists, and how to start. Avoid badges or slogans that displace the reader's task.
- For issues and discussions, preserve reproduction steps, environment, expected behavior, actual behavior, workarounds, and ownership boundaries.
- For pull requests, make the review surface explicit: intent, files touched, behavior changed, tests run, risks, and rollback considerations.
- Disclose generated assets, sponsorship, affiliation, security impact, and private-source boundaries when material.
- Before handoff, verify Markdown rendering, tables, anchors, code fences, relative links, badges, images, alt text, and release archive references.
